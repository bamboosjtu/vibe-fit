# 部署手册

VibeFit 拆为 PWA（纯前端）和 Backend（备份服务）两个独立可部署单元。两者可单独部署、单独扩缩容、单独升级。Android 通过 Capacitor 打包 PWA 构建产物，不参与服务端部署。

本手册按三种环境组织：**本地开发环境**（npm run dev）、**本地 Docker**（docker compose）、**远程树莓派 Docker**（ACR 镜像 + override compose）。

## 顶层目录与服务映射

| 目录 | 构建产物 | 部署单元 |
| --- | --- | --- |
| `pwa/` | nginx 静态镜像（`vibefit-frontend`） | 独立容器，不依赖 backend |
| `backend/` | Fastify API 镜像（`vibefit-backend`）+ Worker 镜像（`vibefit-worker`） | 独立容器栈（postgres + backend + worker） |
| `android/` | APK / AAB | 移动端安装包，不部署到服务器 |
| `docs/` | — | 文档，不部署 |

## 一、本地开发环境

适合日常开发调试，前后端可独立启动，互不依赖。

### 1.1 PWA 前端（Vite dev server）

PWA 是纯前端离线应用，不依赖 backend 即可完整运行。

```bash
cd pwa
npm install
npm run dev          # Vite dev server，默认 :5173
npm run build        # tsc -b && vite build → dist/
npm run lint         # ESLint
npm test             # Vitest
```

启动后访问 `http://localhost:5173`。本地数据存于浏览器 IndexedDB（Dexie），无网络也能记录训练。

### 1.2 Backend（Fastify API + Worker）

后端开发需要 PostgreSQL 实例。可用本机 PostgreSQL，或单独启动 backend compose 的 postgres 服务：

```bash
cd backend
npm install
cp .env.example .env        # 至少设置 32 字符的 JWT_SECRET 与 SMTP 参数
# 单独启动 postgres（不启动 backend/worker 容器）
docker compose up -d postgres
# 或使用本机 PostgreSQL，将 DATABASE_URL 写入 .env

npm run db:push             # prisma db push，本地 schema 同步（开发期使用）
npm run dev                 # API（:8080），watcher 模式
npm run dev:worker          # Worker（独立终端，watcher 模式）
npm run typecheck
npm run build
```

启动后访问 `http://localhost:8080/health`。

### 1.3 前后端联调

- 前端 dev server 默认走相对 `/api/*` 路径。开发时通过 Vite proxy 或在 `.env` 中设置 `VITE_API_BASE_URL=http://localhost:8080` 直连后端。
- 后端 `CORS_ORIGIN` 必须包含前端实际访问的 origin（同时放行 `http://localhost:5173` 与 `http://127.0.0.1:5173`）。

## 二、本地 Docker

适合集成测试、Demo 演示。前后端独立 compose，可单独启动或同时启动联调。

### 2.1 PWA 前端容器栈

[`pwa/docker-compose.yml`](../pwa/docker-compose.yml) 仅编排 `frontend` 容器（nginx + 构建产物 + Service Worker）。

```bash
cd pwa
docker compose up -d --build
# 访问 http://localhost:8081
```

PWA 不依赖 backend 容器。nginx 反代 `/api/*` 到 upstream `backend`（同 Docker 网络时生效），未启动 backend 时仅云端备份失败，本地功能不受影响。

### 2.2 Backend 容器栈

[`backend/docker-compose.yml`](../backend/docker-compose.yml) 编排三服务：`postgres + backend + worker`。依赖链：`PostgreSQL healthy → Worker healthy → Backend healthy`。

```bash
cd backend
cp .env.example .env        # 设置 JWT_SECRET + SMTP 参数
docker compose up -d --build --wait
docker compose ps --all     # postgres/backend/worker 均 running/healthy
sh scripts/acceptance.sh    # 部署验收
```

服务端口：

| 服务 | 地址 |
| --- | --- |
| Backend API | `http://localhost:8080` |
| PostgreSQL | `localhost:5432`（开发密码见 compose） |

#### 数据库 schema 初始化

走 PostgreSQL 镜像标准 `/docker-entrypoint-initdb.d/` 机制：[prisma/init.sql](../backend/prisma/init.sql) 挂载为只读 init 脚本，**仅在数据卷首次创建时执行**，后续重启不会重复跑。`init.sql` 全部使用 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，幂等安全。

| 场景 | 执行方式 |
| --- | --- |
| 本地首次启动 | postgres 容器自动执行挂载到 `/docker-entrypoint-initdb.d/init.sql` 的 init 脚本 |
| 本地 schema 变更后 | `docker compose down -v` 删卷重建（仅本地开发，会丢数据） |
| 本地开发同步 schema | `npm run db:push`（prisma db push） |

### 2.3 前后端容器联调

同时启动两端 compose，前端 nginx 通过 Docker 网络反代 `/api/*` 到 `backend` 容器：

```bash
# 终端 1：后端
cd backend && docker compose up -d --build

# 终端 2：前端
cd pwa && docker compose up -d --build
# 访问 http://localhost:8081
```

注意：两端 compose 默认各自的 Docker 网络。要让 nginx 通过容器名 `backend` 解析到后端，需将前端容器加入后端的 Docker 网络，或使用外部网络。简化做法是在 `pwa/.env` 中设置 `VITE_API_BASE_URL=http://localhost:8080` 直连后端。

### 2.4 验收脚本

```bash
cd backend && sh scripts/acceptance.sh
cd pwa && sh scripts/acceptance.sh
```

- 后端验收：长期服务状态、健康检查、版本接口、镜像隔离（含 Prisma Client 不含 Prisma CLI）
- 前端验收：容器状态、HTTP 200、SPA fallback、Service Worker 资源

### 2.5 常用命令

```bash
cd backend
docker compose logs --follow backend worker
docker compose restart backend worker
docker compose down
```

删除 `vibe_fit_pg_data` 会永久清除本机数据库，普通重启或升级不要使用 `docker compose down -v`。

## 三、远程树莓派 Docker

适合生产部署。树莓派（ARM64）只引用已发布到 ACR 的不可变镜像 digest，不在仓库内维护专用 compose 或运维脚本。

### 3.1 前置条件

- ARM64 树莓派（4/5 或同等 Linux ARM64 主机）
- Docker 24+ 与 Docker Compose v2
- 已发布到阿里云 ACR 的多架构镜像（`linux/arm64` 必须存在）
- 已生成的 `images.lock.env`（开发机执行 `publish-acr.sh` 后产出）

### 3.2 镜像发布（在开发机执行）

在开发机上发布镜像到 ACR，产出包含 `sha256:` digest 的锁文件：

```bash
# 后端：发布 vibefit-backend + vibefit-worker，写入 backend/scripts/images.lock.env
cd backend
ACR_REGISTRY=crpi-xxx.personal.cr.aliyuncs.com \
ACR_NAMESPACE=vibefit \
RELEASE_VERSION=1.1.0 \
./scripts/publish-acr.sh

# 前端：发布 vibefit-frontend，写入 pwa/scripts/images.lock.env
cd pwa
ACR_REGISTRY=crpi-xxx.personal.cr.aliyuncs.com \
ACR_NAMESPACE=vibefit \
RELEASE_VERSION=1.1.0 \
./scripts/publish-acr.sh
```

前后端独立发布、独立锁文件。锁文件记录 `sha256:` digest，部署侧通过 `docker-compose.override.yml` 引用具体 digest，**不接受 `latest` tag**。

发布脚本验证项：
- 必须同时存在 `linux/amd64` 与 `linux/arm64` 多架构
- digest 必须匹配 `^sha256:[0-9a-f]{64}$`
- 工作区必须干净（除非显式 `ALLOW_DIRTY_BUILD=true`）

### 3.3 树莓派 compose 示例

仓库不提供专用 compose。运维基于 `backend/docker-compose.yml` 与 `pwa/docker-compose.yml` 在自己环境创建 `docker-compose.override.yml`，引用具体 digest：

```yaml
# docker-compose.override.yml（运维在自己环境维护）
services:
  postgres:
    # 使用外部已存在的 PostgreSQL 或自建卷
    volumes:
      - pg_data:/var/lib/postgresql/data
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro

  backend:
    image: crpi-xxx.personal.cr.aliyuncs.com/vibefit/vibefit-backend@sha256:...
    environment:
      DATABASE_URL: postgresql://user:pass@postgres:5432/vibefit
      JWT_SECRET: ${JWT_SECRET}
      SMTP_*: ${SMTP_*}
      ADMIN_TOKEN: ${ADMIN_TOKEN}
      CORS_ORIGIN: https://your-domain
    # 不使用 build:
  worker:
    image: crpi-xxx.personal.cr.aliyuncs.com/vibefit/vibefit-worker@sha256:...

  frontend:
    image: crpi-xxx.personal.cr.aliyuncs.com/vibefit/vibefit-frontend@sha256:...
    ports:
      - "80:80"
      - "443:443"
```

部署原则：
- 只引用不可变 ACR 镜像 tag（来自 `images.lock.env`），**不使用 `latest`**
- secrets 通过环境变量或 Docker secrets 注入，**不写入仓库**
- HTTPS 终止在独立网关层（Caddy / nginx），内部服务走 Docker 网络

### 3.4 数据库初始化

后端运行时镜像**不含 psql、不含 Prisma CLI、不含 migrate 入口**。所有 schema 操作都在容器外完成。

```bash
# 在树莓派主机或可访问 PostgreSQL 的机器上执行
psql $DATABASE_URL -f backend/prisma/init.sql
```

`init.sql` 全部使用 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，幂等安全，可重复执行。

| 场景 | 执行方式 |
| --- | --- |
| 生产首次部署 | 运维 `psql $DATABASE_URL -f prisma/init.sql` |
| 生产 schema 变更 | 运维编写增量 SQL，review 后手动执行 |

### 3.5 备份与巡检

仓库刻意不为某种部署目标（树莓派、K8s、云主机）维护专用目录，避免出现「特殊打包专用目录或文件」。备份/巡检由运维用自己工具链承担：

- PostgreSQL 数据备份：`pg_dump` / `restic` / 云厂商快照
- 容器日志：`docker compose logs` / 集中日志方案
- 健康巡检：`curl https://your-domain/healthz` / 外部 Uptime Check

## 共享约束

不论哪种部署环境，以下约束都必须遵守：

### CORS

`CORS_ORIGIN` 必须同时放行 `localhost` 和 `127.0.0.1` 变体（包括 `http://` 与 `https://`），避免来源不匹配。生产只允许 HTTPS origin，禁止通配符。

### HTTPS

- 必须在独立网关层（Caddy / nginx）终结，内部服务走 Docker 网络
- 本地 HTTPS 联调必须显式声明 `https://localhost, https://127.0.0.1` 主机名
- 任何环境都不以 `curl -k` 绕过 TLS

### Fastify trustProxy

Fastify 必须启用 `trustProxy: true`，确保 `request.protocol` 与 `request.ip` 通过代理后准确。

### 反代端点

Caddy/nginx 必须暴露以下端点：

- `/api/*` — 业务接口
- `/health` `/healthz` `/readyz` — 存活与就绪探针

### Service Worker

PWA 必须使用 `vite-plugin-pwa` 管理的 SW，配置 `autoUpdate` + `skipWaiting: true` + `clientsClaim: true`，避免缓存旧 JS bundle。**不手动注册 SW**。

### 镜像隔离

- 运行时镜像不得包含 TypeScript / tsx / Prisma CLI / psql / 源码 / 测试
- 镜像 tag 必须包含 Git commit SHA + Build ID，不允许仅 `latest`
- Worker 镜像必须自带 `CMD ['node', 'dist/worker.js']`，不依赖 compose 覆盖
