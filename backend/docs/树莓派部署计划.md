## 1. 本次检查结论

已通过 SSH 完成磁盘检查和第一轮低风险优化。没有修改任何分区、挂载、Docker、PostgreSQL 或 systemd 配置。

- microSD 已使用整个设备，没有可扩展的尾部未分配空间。
- `BAMBOO` 是部署者的独立可移动 NTFS 数据盘，不作为 VibeFit 的启动、Docker 或 PostgreSQL 依赖；不写入 `/etc/fstab`，不改分区。
- 已删除明确授权的 Playwright、node-gyp、pip、npm/npx 与 APT 可重建缓存，未删除软件、项目源码、日志、交换文件或用户文档。
- 完成缓存与重复软件清理后，microSD 可用空间由约 3.82GB 增至约 11.85GB，根分区使用率由 87% 降至 60%。
- 清理后对根文件系统成功执行 fstrim，trim 约 6.6GiB 空闲块；温度 38.9°C、`get_throttled=0x0`，没有新增 I/O 或低电压错误。
- 当前采用 microSD 独立部署方案。首次拉取真实镜像后必须再次核对空间；如根分区达到 80%，停止部署并重新评估软件精简或存储方案。

## 3. 磁盘检查结果

### 3.1 microSD：`/dev/mmcblk0`

设备信息：

- 设备标识：`SC32G`
- 类型：SD
- 卡片生产日期字段：`09/2020`
- 总容量：31,914,983,424 字节
- 分区表：DOS/MBR
- 根文件系统：ext4，挂载参数包含 `noatime`
- 当前 fstrim timer：active、enabled
- 当前文件系统状态：clean

分区边界：

| 分区 | 起始扇区 | 结束扇区 | 用途 |
| --- | ---: | ---: | --- |
| `/dev/mmcblk0p1` | 8,192 | 1,056,767 | 512MB FAT32，`/boot/firmware` |
| `/dev/mmcblk0p2` | 1,056,768 | 62,333,951 | ext4，`/` |

设备最后一个扇区也是 `62,333,951`。除开头用于对齐的约 4MiB 外，microSD 没有可利用的未分配区域，不能通过扩展分区增加空间。

该卡是否属于高耐久系列无法从系统字段确认，而且生产日期字段已接近六年。经缓存清理后它具备首次部署的空间，但长期运行风险仍高于高耐久新卡。部署必须保留 PostgreSQL 一致性设置、Docker 日志上限、定期 fstrim、空间阈值和异机备份，不能把 30 天通过等同于 microSD 多年耐久证明。

### 3.2 外置 SSD：`/dev/sda`

设备信息：

- 型号：`WDC WDS480G2G0A-00JH30`
- 容量：480,103,981,056 字节（447.13GiB）
- USB 桥：Ugreen / ASMedia `174c:225c`
- 链路：USB 3.0 5Gbps
- 驱动：UAS
- 旋转标志：0，确认为 SSD
- 分区表：DOS/MBR
- 文件系统：NTFS，通过内核 `ntfs3` 驱动读写挂载
- 卷标：`BAMBOO`
- 当前挂载：`/media/cu2z/BAMBOO`
- 已用：约 16.39GB
- 可用：约 463.71GB
- `/etc/fstab`：没有持久化条目；当前挂载依赖桌面会话自动挂载

当前唯一分区 `/dev/sda1` 从扇区 4,096 延伸到 937,701,375；设备最后扇区为 937,703,087。尾部只剩 1,712 个扇区，约 856KiB，不构成可用的部署空间。

SSD 的 Linux discard 参数为 0，说明当前 USB-SATA 桥或固件没有向内核传递 TRIM。由于 `BAMBOO` 不承载 VibeFit 运行数据，这不是应用部署阻断项。若将来要把它用于长期高写入任务，再补做 SMART、备份和桥接兼容性评审。

## 4. 目标存储拓扑

| 位置 | 目标用途 | 说明 |
| --- | --- | --- |
| microSD `/` | Raspberry Pi OS、Docker data-root、容器日志 | 当前可用约 11.85GB；生产日志严格限制为每容器 `3 × 10MB` |
| microSD `/opt/vibefit` | 发布脚本、Compose、镜像锁、Caddy 配置 | 主要为只读文件 |
| microSD `/srv/vibefit/data/postgres` | PostgreSQL 15 主数据 | 保持 fsync、full page writes、同步提交和数据校验和 |
| microSD `/srv/vibefit/backup-work` | 临时备份/恢复工作区 | 不是灾难备份，完成后及时清理 |
| `BAMBOO` | 独立可移动个人数据盘 | 不写 fstab，不作为启动依赖，不存放运行中的 PostgreSQL/Docker 数据 |
| NAS、第二块备份盘或远端仓库 | Restic 加密备份 | 必须与 microSD 分离 |

Docker 保持默认 `/var/lib/docker`。应用正式发布后，每次拉取、升级和数据库快照前都要执行空间预检；空间不足时停止操作，不能通过关闭 PostgreSQL 一致性设置或压缩系统保留空间来勉强上线。

## 5. BAMBOO 使用策略

1. 保持现有 NTFS、卷标、数据和桌面自动挂载方式不变。
2. 不把 `BAMBOO` 写入 `/etc/fstab`，树莓派在 SSD 未连接时仍应完整启动 VibeFit。
3. 不把 Docker data-root、PostgreSQL 数据目录、升级工作目录或 systemd 依赖指向 `BAMBOO`。
4. 可以在人工连接后，把 `BAMBOO` 作为一次性加密备份目的地；备份完成、校验通过并安全卸载后可带离树莓派。
5. 如果以后需要自动备份，应优先使用 NAS 或另一块专用备份介质，而不是把个人数据盘永久绑定到树莓派。

## 7. microSD 部署空间策略

1. ext4 继续保留当前约 5% root reserved blocks，不为美化使用率而降低文件系统保护空间。
2. Docker 保持默认 `/var/lib/docker`；Compose 的日志轮转上限必须保持为每容器 `3 × 10MB`。
3. PostgreSQL 数据位于 `/srv/vibefit/data/postgres`，保留所有一致性设置并限制连接数和日志量。
4. 首次部署只拉取 `1.1.0` 不可变 digest；拉取后立即检查 `docker system df` 和根分区使用率。
5. 只有当根分区仍低于 80%、可用空间足以容纳一次校验后的数据库 dump 和至少 2GB 系统安全余量时才启动服务。
6. 首次升级前必须同时缓存当前版和候选版；若此时达到 80%，停止升级并先确认精简 OnlyOffice/Snap/Flatpak或调整存储。
7. 升级快照完成并确认不再需要后按手册保留策略清理，不在 microSD 无限累积。
8. 保持每周 fstrim timer；不需要高频手工 fstrim。
9. 监控 root 使用率、PostgreSQL 大小、Docker 镜像占用、swap I/O 和内核 mmc/EXT4 错误。

## 8. 主机与网络 Go/No-Go

1. 路由器为树莓派固定 `192.168.31.181` 的 DHCP 租约。
2. 确定 `VIBEFIT_HOST`：
   - 推荐固定局域网 DNS 名；或
   - 使用证书 SAN 中明确包含的 `192.168.31.181`。
3. 在可信通道核对 SSH 主机密钥。
4. 配置并验证 SSH 公钥，再决定是否关闭口令认证。
5. 评估 3389/5900 是否继续保留；防火墙启用前必须先验证 SSH 和物理恢复通道。
6. 重启后确认 NTP 已同步、80/443 空闲、systemd 无失败单元。

## 10. HTTPS、secret 与首次部署

部署者必须提供：

- ACR endpoint、namespace、用户名和访问密码；
- `VIBEFIT_HOST`；
- 私有根 CA 公钥；
- SAN 匹配 `VIBEFIT_HOST` 的叶子证书和私钥；
- PostgreSQL、DATABASE_URL、JWT、SMTP 与 Restic secret；
- SMTP 主机、账号和发件地址；
- 与 microSD 分离的备份目的地。

根 CA 私钥必须离线保存，不能进入仓库、构建机发布目录或树莓派。

首次部署顺序：

1. 把发布包复制到 `/opt/vibefit`。
2. 在 microSD 根文件系统创建 `/srv/vibefit/data`、升级快照和恢复工作目录，并确认没有路径指向 `BAMBOO`。
3. 写入 `config.env`、真实镜像锁和 secret 文件，并设置权限。
4. 使用 root Docker 凭据登录 ACR。
5. 预拉取六个不可变 digest 镜像并复核 microSD 空间；达到 80% 立即终止部署。
6. 运行发布配置校验、一次性数据库迁移、服务启动和健康等待。
7. 使用私有根 CA 验证 Caddy HTTPS、H5、`/health` 和 `/api/version`，禁止 `curl -k`。
8. 确认只有 Caddy 暴露 80/443，PostgreSQL、Backend、Worker 和 Frontend 没有宿主端口。

## 11. Android、备份、升级与 30 天验证

### Android/H5

1. Android `1.1.0 / versionCode 83` 构建时注入私有根 CA 公钥。
2. 真机配置 HTTPS 服务地址，完成邮件登录。
3. 上传快照，确认 Worker 消费。
4. 清空测试本地数据后恢复最新快照。
5. 验证非法恢复不会覆盖本地数据，H5 保持同源访问。

### PostgreSQL 备份

1. 自动备份 timer 默认关闭。
2. 先在独立测试卷完成 dump、销毁、恢复和内容比对。
3. PostgreSQL 主数据和升级工作区都在 microSD，同卡副本不算灾难备份。
4. 可在人工连接 `BAMBOO` 时创建加密 Restic 备份，验证完成后安全卸载；这不能成为 VibeFit 启动依赖。
5. 更推荐配置 NAS、专用第二块磁盘或远端 Restic 仓库，再手工完成一次加密备份、完整性检查和隔离恢复。
6. 只有具备稳定、独立且自动可用的备份目的地后，才启用 03:15 定时器。

### 升级、回滚与稳定性

1. 升级前缓存当前版和候选版 digest。
2. 生成并校验升级前 PostgreSQL dump。
3. 完成一次候选版升级、镜像回滚和隔离数据库恢复。
4. 启用每 5 分钟观测，重点记录 microSD 空间、mmc/EXT4 错误、Docker 占用、PostgreSQL 大小和 swap I/O；`BAMBOO` 是否连接不影响健康判定。
5. 第 0、7、14、21、30 天完成 Android 上传/恢复往返。
6. 安排主机重启、Backend/Worker/PostgreSQL 强制终止恢复。
7. 第 30 天生成报告；任何代码、镜像或 schema 修复都重新从 Day 0 计时。

## 12. 存储阶段验收条件

以下条件全部满足后才能发布 VibeFit：

- `BAMBOO` 未写入 VibeFit 配置、Docker data-root、PostgreSQL 路径或 systemd 启动依赖；
- 拔除 `BAMBOO` 后树莓派和 VibeFit 仍能正常启动；
- microSD 当前根分区低于 75%；
- 拉取正式镜像后根分区仍低于 80%；
- 首次升级缓存当前版和候选版后仍能容纳校验后的数据库 dump 与至少 2GB 系统安全余量；
- Docker 日志轮转和 PostgreSQL 日志限制已经生效；
- 负载测试中没有 mmc、EXT4、I/O、低电压、降频或持续 swap 写入；
- 外部灾难备份未配置时，备份 timer 保持关闭并明确记录风险。
